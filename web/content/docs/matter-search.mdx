---
title: Matter search
description: Search matter documents with keyword, semantic, or hybrid retrieval plus metadata filters and facets.
---

Matter search is a rebuildable OpenSearch projection of authoritative Core and Artifact data. An OpenSearch outage or indexing delay does not change the source document or metadata records.

## Who can use it

Matter administrators can submit searches, inspect index generations and projection operations, and request a rebuild. Core authorization always adds the current tenant and matter scope; callers cannot replace that scope or submit raw OpenSearch Query DSL.

## Index lifecycle

Creating a matter records a durable schema-sync operation. Adding searchable metadata definitions records another sync, while adding documents or changing a searchable asserted metadata value records document-upsert operations. The workflow worker applies these operations asynchronously. Metadata writes update the Core current-value projection before they commit, so an indexing delay affects only search freshness—not the document view or metadata history.

User-driven document updates use the highest queue priority so an interactive tag or text change is not trapped behind a corpus job. Import and agent batches use lower priority, and full rebuilds use the lowest priority. All lanes use the same idempotent projection workflow and remain observable as operations.

Search work is serialized per matter with a PostgreSQL advisory transaction lock. It does not lock the authoritative matter row, so slow artifact reads and OpenSearch writes cannot block document ingestion through the matter foreign key. Different matters may still project concurrently. If an interrupted generation attempt leaves a physical OpenSearch index without a committed Core generation record, the next attempt skips that orphaned name and allocates a new generation.

Schema changes are planned before they are applied. A new searchable metadata field is added to the active mapping in place. If documents already have current asserted values for that field, only those document projections are refreshed; an empty new field requires no document backfill. Changes that alter an existing mapping pause for administrator confirmation. These include field type, analyzer, or facet-representation changes; vector configuration changes; removing or renaming fields; and incompatible nested/object shape changes.

After confirmation, the worker creates and populates a new physical index and atomically moves the matter's stable alias only when the replacement is ready. It then deletes non-active physical indexes followed by their generation records. Recent projection operations remain available as the audit and diagnostic history.

The matter's **Search index** tab shows the active generation, indexed and authoritative document counts, current workflow activity, and recent projection operations. During a full rebuild it reports the current phase, documents processed, total documents, percentage, and target physical index after every successful bulk batch. This progress is stored on the durable operation, so refreshing or leaving the page does not lose it. The indexed count is read from the active OpenSearch generation after each successful update, so it may trail Core while import batches are still projecting. When a schema change requires reindexing, the tab explains why and asks a matter administrator to confirm. An administrator can also request a complete rebuild directly. The current active index remains searchable until its replacement is fully populated and activated.

If one or more document-update jobs fail, select **Requeue failed jobs** on the Search index tab. The retry count includes operations marked failed by the application and operations stranded as running after their durable workflow ended in an error, such as when PostgreSQL or a worker stopped during error handling. Confirming the action assigns each retryable operation a fresh durable workflow ID and queues it again. Already indexed document IDs are updated idempotently rather than duplicated. The action retries only failed or interrupted document updates; failed full rebuilds and schema operations remain visible for separate diagnosis.

OpenSearch capacity failures use durable exponential backoff instead of rapid retries. Disk flood-stage blocks, request throttling, circuit breakers, rejected execution, unavailable shards, temporary connection failures, and temporary cluster-manager failures are retried from 30-second intervals up to one-hour intervals. Permanent mapping or validation errors fail immediately. The projection saves its progress after every accepted bulk request and retains rejected document IDs, so a retry resumes at the failed page instead of indexing the whole matter again. If an embedding job exhausts the pressure-recovery window after its vectors have already been generated, select **Retry indexing** on the Jobs tab to reuse the completed embeddings and resume only the unfinished OpenSearch projection.

The same status and control surfaces are available through the API. Use `GET /v1/matters/{matter_id}/search-operations` to inspect queued, running, action-required, completed, or failed work. Use `GET /v1/matters/{matter_id}/search-operations/retryable` to count failed application operations plus durable-workflow errors that are safe to retry. Use `GET /v1/matters/{matter_id}/search-indexes` to inspect the active physical generation. Retry all currently failed or interrupted document updates with `POST /v1/matters/{matter_id}/search-operations/retry-failed`. Confirm a requested schema reindex with `POST /v1/matters/{matter_id}/search-operations/{operation_id}/confirm-reindex`. An administrator can request a complete rebuild directly with `POST /v1/matters/{matter_id}/search-indexes/rebuild`.

## Query behavior

Semantic and hybrid searches may use a dedicated query embedding model. With `EMBEDDING_QUERY_MODEL=voyageai/voyage-4-nano`, document vectors can remain on hosted `voyage-4-lite` while query vectors are generated locally in the compatible Voyage 4 embedding space. Query inference uses `input_type=query` and the same dimensions and normalization as document vectors.

`POST /v1/matters/{matter_id}/search` accepts a controlled request containing:

- a query and `KEYWORD`, `SEMANTIC`, or `HYBRID` search mode;
- an optional `minimum_similarity` from `0` to `1` for thresholded Semantic searches;
- optional searchable field keys;
- typed `EQ`, `IN`, `RANGE`, `EXISTS`, and `NOT_EXISTS` filters;
- configured facetable field keys;
- controlled sort fields; and
- pagination.

Text fields use versioned eDiscovery analyzer names for indexing, ordinary search, and phrase search. The initial three profiles all use the standard tokenizer plus lowercase normalization, preserve token positions and offsets, and do not remove stop words. This supports ordinary keyword queries and quoted phrases while allowing the profiles to evolve independently later. Facetable text fields also receive an exact keyword subfield; identifiers and enum values remain keywords.

Semantic vectors use the OpenSearch FAISS engine with an HNSW index and cosine similarity. Keyword search continues to use Lucene, while Hybrid search combines the keyword and FAISS-backed semantic result lists through the matter search pipeline. Changing the vector engine or HNSW configuration requires a new physical index generation and a full reprojection.

Semantic search without a minimum similarity is top-k retrieval: the matter workspace ranks a stable window of up to 1,600 candidates, and every eligible vector has some nearest-neighbor score. Paging through results does not enlarge or otherwise change that window. The UI therefore labels the count as semantic candidates rather than exact matches. Set **Min similarity** to a cosine-similarity value from `0` through `1` to use FAISS radial search; decimal values such as `.035` are accepted. Lower values include more loosely related documents, while higher values return fewer, more closely related documents. Leave the field blank to use the candidate window. The application converts the user-facing cosine value into OpenSearch's internal FAISS score. Thresholds are supported only for Semantic search because Hybrid's reciprocal-rank-fusion score is on a different scale.

Hybrid search uses a stable reciprocal-rank-fusion depth of 100 results per shard on every results page. This is separate from Semantic search's 1,600-document candidate window: the smaller Hybrid depth keeps OpenSearch's multi-shard RRF processor responsive while supporting page two and later with active filters. Moving between pages preserves the same fusion depth and ranking basis.

Hybrid result retrieval uses the RRF search pipeline. Facet counts and date histograms are aggregation-only requests and do not need fused document scores, so they execute the same controlled Hybrid query without the RRF phase-results processor. This avoids OpenSearch query/fetch count errors when an aggregation intentionally requests zero document hits.

## Keyword search syntax

Keyword and the keyword portion of Hybrid search use OpenSearch's `simple_query_string` parser. This intentionally provides a forgiving, controlled syntax: malformed fragments are ignored instead of causing the entire search to fail. It is not the full OpenSearch Query DSL.

Unquoted text is case-insensitive and is analyzed into words. All terms are required by default, so:

```text
price coordination
```

finds documents containing both `price` and `coordination`. The words do not need to be adjacent or in that order. Punctuation normally separates words. There is no stemming or stop-word removal, so `investigate` and `investigation` are different terms unless you use a prefix or fuzzy search.

### Operators

| Purpose | Syntax | Example | Meaning |
| --- | --- | --- | --- |
| AND | a space or `+` | `price + coordination` | Require both clauses. Because AND is the default, `price coordination` has the same effect. |
| OR | `\|` | `terminate \| cancel` | Match either clause. |
| NOT | `-` immediately before a term or group | `pricing -draft` | Require `pricing` and exclude documents containing `draft`. |
| Exact phrase | double quotes | `"price coordination"` | Match the analyzed words next to one another and in the stated order. |
| Grouping | parentheses | `pricing + (fixing \| coordination)` | Control how mixed Boolean clauses are combined. |
| Prefix | `*` at the end of a term | `investigat*` | Match terms beginning with `investigat`, such as `investigate` and `investigation`. |
| Fuzzy term | `~n` after a term | `recieve~1` | Allow approximately `n` character edits, useful for misspellings and OCR errors. |
| Phrase proximity | `~n` after a quoted phrase | `"price meeting"~3` | Allow the phrase terms to occur within the specified positional distance. |

Use symbolic operators exactly as shown. `AND`, `OR`, and `NOT` typed as words are searched as ordinary words; they are not Boolean operators in this search box.

When combining AND and OR, always use parentheses to make the intent explicit:

```text
(contract | agreement) + (terminate | cancel*) -draft
```

This requires either `contract` or `agreement`, also requires either `terminate` or a word beginning with `cancel`, and excludes `draft`.

For exclusion, include a positive clause whenever possible. For example, use `responsive -privileged` rather than a negative-only query such as `-privileged`. A positive anchor produces clearer and more predictable matching and scoring.

### Phrases and proximity

Quotes mean an analyzed phrase, not a byte-for-byte substring. Search remains case-insensitive, and punctuation is handled by the tokenizer:

```text
"Project Falcon"
```

matches the adjacent tokens `project` and `falcon`. To allow intervening words, add phrase proximity:

```text
"Project Falcon"~4
```

Use a small proximity value first. Larger values broaden the search and can reduce precision.

### Prefixes, wildcards, and fuzzy terms

The supported wildcard form is a trailing `*`, which performs prefix matching:

```text
privileg*
```

Leading or embedded wildcards such as `*ileged` or `priv*ged`, the `?` single-character wildcard, regular expressions, and SQL `%` wildcards are not supported by the current matter search syntax. Use a normal term, trailing prefix, fuzzy term, phrase, or metadata filter instead.

Fuzzy matching uses edit distance:

```text
seperate~1
```

This can compensate for a small spelling or OCR error. Prefer `~1` or `~2`; broad fuzzy clauses can match surprising terms and cost more to evaluate. Do not combine fuzzy and prefix operators on the same term.

### Escaping reserved characters

The reserved syntax characters are:

```text
+ | - * " ( ) ~ \
```

Type a backslash before a reserved character when it should not act as an operator. In the browser search box, use one backslash, such as `\-` for a literal hyphen or `\*` for a literal asterisk. Escaping prevents syntax interpretation, but punctuation can still be removed by the text analyzer and therefore may not be independently searchable.

### Syntax that is not supported in the search box

Do not use the following full-query-string or Query DSL forms:

- `field:value` field qualification;
- `[10 TO 20]`, `>10`, or other inline ranges;
- `/regular expressions/`;
- leading, embedded, or `?` wildcards;
- raw OpenSearch JSON; or
- SQL or PPL expressions.

Use the field controls and typed metadata filters for exact values, field restriction, dates, numbers, and ranges. The browser never sends raw OpenSearch DSL.

### Search mode interaction

- **Keyword** interprets all of the syntax above.
- **Semantic** treats the complete entry as natural-language text. Boolean and wildcard characters do not constrain semantic retrieval.
- **Hybrid** interprets the syntax in its keyword branch and also sends the complete entry to semantic retrieval. For the cleanest semantic meaning, avoid unnecessarily complicated Boolean expressions in Hybrid searches.

The implementation follows the [OpenSearch simple query string syntax](https://docs.opensearch.org/latest/query-dsl/full-text/simple-query-string/), with AND configured as the default operator and wildcard analysis enabled.

## Metadata filters, fields, facets, and sorting

Search-box syntax is for analyzed text. Structured metadata is handled separately so values can be validated against the matter's active searchable field definitions.

| Filter | Supported fields | Behavior |
| --- | --- | --- |
| `EQ` | Any searchable field except JSON | Exact matching for enums and facetable fields. Non-facetable Text and Long text use analyzed phrase matching. |
| `IN` | Facetable fields | Match any value in the supplied list. Values within one `IN` filter are ORed. Set `include_missing` to also match documents with no indexed value. |
| `RANGE` | Integer, Decimal, Date, and Datetime | Inclusive lower and upper bounds. Either bound may be omitted. |
| `EXISTS` | Any searchable field except JSON | Require that the field has an indexed value. |
| `NOT_EXISTS` | Any searchable field except JSON | Require that the field has no indexed value. |

Separate filters are ANDed. In the workspace, selecting several values in one facet broadens that facet, while selecting values in different facets narrows the result. The `-term` search-box operator excludes an analyzed text term; use **No value** when the requirement is that an exact metadata field has no indexed value.

### Combining facet values

Values selected within the same field are combined with **OR**. For example, selecting `A` and `B` for one multi-value field means “the field contains `A` or `B`.” A document containing both values also matches.

| Document values | Matches selected `A` or `B`? |
| --- | --- |
| `A` | Yes |
| `B` | Yes |
| `A`, `B` | Yes |
| `C` | No |
| Field missing | No |

Every ordinary facet also reports a **No value** bucket. Selecting it by itself uses `NOT_EXISTS`. Selecting **No value** together with ordinary values keeps the within-field OR behavior: for example, selecting `A` and **No value** matches documents containing `A` plus documents with no indexed value for that field. Missing means the field is absent or has no indexed values; it does not mean an indexed empty string.

Selections in different fields are combined with **AND**. For example, selecting `Issue = A` and `Privilege = Privileged` requires a document to match at least one selected Issue value and at least one selected Privilege value.

The facet controls do not yet support excluding a specific populated value, so they cannot express “contains `A` and does not contain `B`.”

Text field definitions can enable **Normalize values to lowercase**. When enabled, every single or multi-value string is converted to lowercase in the search projection, and exact filter input is normalized the same way. The standard Email from, Email to, Email CC, and Email BCC fields enable this option by default so address casing does not split facet buckets. Enabling or disabling normalization for an indexed field requires a confirmed full reindex because existing projected values must be rebuilt.

Enum filters use stable enum keys rather than display labels. Date values use ISO `YYYY-MM-DD`; date-times use ISO 8601, preferably with `Z` or an explicit UTC offset. JSON fields cannot be filtered, faceted, or sorted. `IN` requires a facetable field.

The API's `query_fields` option can restrict keyword matching to active searchable Text or Long text metadata field keys. It does not accept OpenSearch field paths. Without that option, the search covers filenames, email subject and address headers, custodians, source path, body text, and all active searchable Text and Long text metadata. Filename and email-subject matches receive a built-in relevance boost.

Facets can be requested only for fields configured as facetable. Sort supports `_score`, `created_at`, and sortable active metadata fields. Non-facetable Text, Long text, and JSON cannot be sorted. Semantic and Hybrid modes support relevance sorting only.

**Keyword** searches exact words and phrases across the configured text fields.
**Semantic** embeds the query with the matter's configured model and compares it
with nested document-chunk vectors. Each result includes its highest-scoring
passage so the reviewer can see why it matched. **Hybrid** runs both retrieval
methods and combines their document ranks with reciprocal-rank fusion. Hybrid is
the best general starting point when the user wants both precise names or phrases
and conceptually related language.

Semantic and hybrid modes require a query and support relevance sorting. Active
tenant, matter, and metadata filters are applied inside vector retrieval. Without
a Semantic threshold, facet counts describe the retrieved candidate set rather
than every vector in the matter. With a threshold, Semantic counts describe the
documents meeting that similarity floor. Hybrid facet counts continue to describe
its bounded fused candidate set.

Integer metadata maps to OpenSearch `long`. Floating-point metadata maps to `double`. Dates, date-times, booleans, enums, and unindexed JSON use corresponding controlled mappings generated from the matter field catalog.

## Search and review workspace

Open a matter and select **Search & Review** to enter the full-screen review workspace. This workspace removes the ordinary administration navigation so the available screen can be used for finding, reading, and coding documents. Use **Matter** in the upper-left corner to return to matter administration.

The workspace has four coordinated areas on a wide desktop:

- **Filters** starts with every filter group closed so the panel remains compact. Open an ordinary facet to see its eight most common values, a **No value** bucket when documents are missing the field, and current counts. Type in **Find** to retrieve up to 20 matching populated values beyond that initial list. Active searchable Date and Datetime definitions instead open a date histogram plus an inclusive **From** and **To** range. Choose Week, Month, or Year for the calendar buckets, or select a non-empty bucket to apply its range. Datetime bounds cover the complete selected UTC days. Counts respect the current query and filters in other groups, while ignoring the field's own selection so its full matching distribution remains visible. Selecting more than one value—including **No value**—within a field broadens that field, while selections across different fields narrow the result set. Long values are clipped within the panel instead of creating horizontal scrolling.
- **Results** shows the matching documents. Select a row to open the source artifact without leaving the search.
- **Document viewer** displays email and text content inline. Email metadata has its own scrollable panel; drag the horizontal divider beneath it up or down to give the message body more or less room. Focus the divider and use the up and down arrow keys for keyboard resizing. Other native file types can be downloaded and opened in their native application.
- **Document details** has separate **Coding** and **Metadata** tabs. Coding contains only editable asserted fields and stages changes until **Save changes** is selected. Metadata shows all fields in document-visible groups as read-only values, including imported, system, and current asserted values.

On desktop, drag the separators between Filters, Results, Document, and Document details to allocate space to the current task. The document viewer grows or shrinks as its neighboring panels are resized. The separators can also be focused and adjusted with the left and right arrow keys.

Choose **Keyword**, **Semantic**, or **Hybrid** beside the search box. Keyword
search covers filenames, source paths, email headers, custodians, searchable
metadata, and indexed document body text. Semantic search is useful for natural
language descriptions such as “messages discussing concealment of pricing
decisions,” even when those exact words are absent. Hybrid search combines both
approaches. When semantic retrieval contributes to a result, its best matching
passage appears beneath the result title.

When **Semantic** is selected, **Min similarity** appears beside the query. Leave it empty to retrieve and rank the top semantic candidates. Enter a value from `0` to `1` to count and return only documents meeting that threshold. Thresholds are retained in the URL and in saved searches.

The results footer supports previous and next navigation, direct entry of a page number, and a **Last** action. Changing pages clears the selected document and preserves the active query, filters, search mode, threshold, and page in the address.

For body text, the indexer uses extracted text when available, then OCR text, then compatible native content such as EML or plain text. Search terms, mode, active facet values and date ranges, the page, and the selected document are retained in the address, so the current workspace can be bookmarked or reopened. On smaller screens, filters and coding open as focused panels and results and document viewing become separate views.

Keyword and Hybrid result cards show up to two matching fragments returned directly by OpenSearch. Matching terms are highlighted in document text, email headers, paths, filenames, and searchable text metadata. When a result is selected, the terms marked by OpenSearch are also highlighted in the displayed document body and the viewer scrolls to the first match. The browser renders document content as text without interpreting it as HTML.

Metadata coding updates Core immediately and queues a high-priority search projection update. After saving, the workspace reports that search is updating, watches the projection operation, and refreshes the result and facet data when it completes. If projection fails, the workspace reports the index error while preserving the successfully saved Core value.

### Bulk tag search results

Matter administrators can apply coding values to documents returned by an active Keyword, Semantic, or Hybrid search. Enter a query or apply at least one filter, open the **Coding** panel, and select **Bulk tag results**. The action is absent when no search or filter is active and is not available in a review batch.

Choose one or more active reviewable asserted fields and their values, confirm the displayed result count, and start the job. A single-value field accepts one value and replaces its current coding. A multi-value field accepts multiple values in the same job and adds all of them without removing existing values. All selected fields are applied in the same bulk operation and the search scope is materialized only once.

The job stores the submitted search with pagination removed and pins the active physical search-index generation. It then materializes the matching document IDs into durable batches before applying coding, so changing the search in the browser does not change the running job's scope. Each document change uses the normal metadata event ledger, audit trail, current-value projection, and search projection workflow. The dialog reports matched, processed, tagged, and failed counts and may be closed while the durable job continues.

Keyword bulk tagging materializes every match. Semantic and Hybrid bulk tagging first freezes the bounded ranked candidate window and then intersects those candidates with the active filters. For example, if **No value** contains 337 documents in the top 1,600 semantic candidates, the job materializes those 337 document IDs rather than asking OpenSearch for a new set of 1,600 filtered neighbors. The dialog identifies the candidate limit and lists every active filter; the final matched count appears after snapshotting. Ranked bulk operations are limited to the current candidate count, up to 10,000 documents, and do not imply that every potentially related document in the matter was selected. For safety, an empty matter search cannot start a bulk tag job; use an explicit query or filter.

## Saved searches

Use **Save search** in the Search & Review header to preserve the current query, search mode, filters, selected search fields, and sort. Pagination is not preserved: a saved search always opens at the first page.

Choose who can use the saved search:

- **Private** is visible only to you.
- **Public** is visible to everyone who can access the matter.
- **Shared** is visible to you and the active matter users you select.

Open **Saved searches** to see every search available to you. Select **Run** to load its query and filters. Running a saved search performs a new search against the matter's current index; it does not reopen a snapshot of the documents that matched when the search was saved. Results can therefore change after documents, coding values, or the search index change.

Only the owner can delete a saved search. Sharing with user groups is planned but is not available yet; select individual users for now.

## Current limitations

The search projection covers document identity, collection-item metadata, email headers, family, custodian data, resolved current metadata values, and body text. At most 10 MiB of text is loaded from an artifact by default; administrators can change this deployment setting. Existing matter documents must be reindexed after body indexing is enabled or after a preferred extracted/OCR artifact is added. Native binary formats without extracted or OCR text do not have a searchable body. Documents without completed chunk-vector artifacts cannot appear from semantic retrieval, although hybrid search can still find them through keyword matching. Unthresholded semantic retrieval is an approximate nearest-neighbor search over a bounded candidate set, so its total and facet counts describe those candidates rather than every potentially related document. Review queues, hit-term navigation, family navigation, group-based saved-search sharing, and a specialized virtualized result grid are not yet available.
