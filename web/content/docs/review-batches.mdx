---
title: Review batches
description: Freeze document sets for assignment, repeated agent runs, and coding comparisons.
---

Review batches give a matter a stable set of documents for review or evaluation. A document can appear in more than one batch, and creating a batch does not copy its file or remove it from the matter.

## Create a batch

Open a matter and select **Batches**, then select **Create batch**. Give the batch a clear name and description. The description is useful for review instructions, evaluation goals, and notes about why the sample exists.

Choose how to select documents:

- **All matter documents** includes every document currently in the matter.
- **Keyword search results** runs the entered query against filenames, paths, searchable metadata, email fields, and document body text.
- **Random matter sample** selects a repeatable random sample from the matter.
- **Random sample from batch** selects from an existing ready batch.
- **Random sample from saved search** runs an accessible Keyword saved search and samples only its matching documents.

Leaving the random sample size empty includes all source documents in a randomized order. The system stores the random seed, so the selection is reproducible.
Saved-search samples require a sample size. Priv-View snapshots the saved search definition, its name and update time, the active physical search generation, and the random seed. Later edits or deletion of the saved search do not change the frozen batch.

Select one or more shared metadata groups to define the coding fields. The system snapshots those fields when the batch is created. Later edits to the matter group do not silently change the batch.

Use **Groups** in the Batches table or review workspace to change that batch snapshot. Check groups to add them, uncheck groups to remove them, then select **Save groups**. Removing a group hides its fields from subsequent batch coding without deleting values already stored in earlier review runs.

## Status

A batch normally moves from **Queued** to **Building** to **Ready**. Its document count is final when it is ready. The system then prepares the batch for search; review opens with searchable documents when that projection is ready. A failed batch remains visible with its error so the selection can be diagnosed. Search-query batches require a ready matter search index.

## Assignment and value visibility

A batch can have one current human assignee. **Only the reviewer’s values** keeps human coding isolated while a reviewer works. **Values from all reviewers** allows reviewers to see one another’s coding. Agent outputs are always isolated by run.

## Review a batch

When a batch is **Ready**, select **Open review** from the Batches table. If the batch is unassigned, opening it assigns it to you. A batch assigned to someone else cannot be opened for coding.

The review workspace shows indexed document titles, the selected document, and the batch's snapshotted coding groups. Search is always restricted to the batch and supports keyword, semantic, and hybrid modes. Facets and facet value type-ahead also remain restricted to the batch. The number beside each result is its stable position in the original frozen batch, even when a query changes the visible order.

Select **Save & next** to save all displayed coding fields as one isolated reviewer result, mark the document reviewed, and advance. A document with no selected field values can still be saved as reviewed. Select **Skip** when the document should remain uncoded but count as processed.

The progress bar counts saved and skipped documents for your review run. Reopening an unfinished batch resumes the same run. When every document has been saved or skipped, the run is complete and becomes read-only.

If the batch uses **Values from all reviewers**, earlier human-review values appear beneath the corresponding field with the reviewer's name. Your edits remain stored under your own run identity. Agent results are not mixed into this panel.

## Assessment analyses and diagnostic topics

A batch created by **Assess against corpus** has an **Analysis** panel beside the source document. It shows the structured Document Summary, Responsiveness Summary, and Clarification Requests. Citation chips such as `¶4` open the exact normalized source paragraph used as evidence. Missing text, failed analysis, partial coverage, and unavailable results are shown explicitly rather than being treated as non-responsive documents.

After synthesis, **Batch topics** appears as a separate facet. These labels describe only the active taxonomy version for this frozen batch. Selecting a value restricts results using the batch ID, active taxonomy ID, and topic key together, so a document that appears in another batch cannot contribute that other batch's topic labels or counts.

Diagnostic batch topics do not change the matter-wide **Topics** metadata created by the approved topic-clustering workflow. A document can have both: matter topics remain corpus-wide metadata, while batch topics remain assessment-only labels inside their batch.

## Chat with a batch

Open any ready, searchable batch and select **Chat** in the right panel. Start a named conversation, then ask a natural-language question. The managed **Batch Chat Agent** converts the question into one or more semantic searches and Core always injects the current batch ID as a required filter. A conversation is permanently bound to that matter and batch; the model cannot broaden its retrieval scope.

The initial evidence source is the newest compatible structured `SUMMARY` artifact for each matching matter document. A summary produced for the current batch is preferred, while a reusable summary from another assessment of the same matter document may be used with its provenance retained. Answers identify supporting document IDs and disclose when semantic candidates lack usable summaries. They do not represent that the agent reviewed the complete native document, and a missing semantic result is not proof that the subject is absent from the batch.

Batch chat requires a ready search projection, document embeddings for semantic retrieval, and summary artifacts for answer evidence. A batch may be opened before all three are available, but the chat panel explains which prerequisite is missing rather than silently falling back to unscoped matter search or source document text. Switching the answer evidence from summaries to full document content is a future extension of the retrieval contract.

## Evidence in Batch Coding analysis

When a published analysis task requires evidence, the JEV request asks the task's decision questions and companion evidence questions together. JEV checks whether document evidence exists and ranks the document's numbered paragraphs for each required decision. Priv-View validates the selected paragraph identifiers before storing them with the immutable decision result. Matter guidance is decision context; it is never stored as document evidence.

A result is complete only when every required decision question has a qualifying document paragraph at or above its configured evidence-existence threshold. Missing or weak evidence remains visible as partial coverage and does not erase the underlying typed decision. Evidence localization currently supports up to 255 numbered paragraphs in one request. A longer document remains partial until windowed evidence localization is available; Priv-View does not silently search only part of it.

The Batch Chat panel uses the same authenticated lifecycle stream as Matter Definition Chat. A **Live** indicator means normal conversation polling is disabled. The panel reconnects from its last durable event cursor after a transient interruption and automatically restores polling after repeated stream failures. Assistant text is displayed when the final message is committed; token-by-token output is not streamed.

## Agent evaluation

Each human or agent pass receives a separate run identity. Re-running an updated agent against the same batch creates a new run and preserves the earlier output. The two runs—or an agent run and a human reference run—can then be compared field by field.

Run results do not change the matter’s ordinary metadata. A manager may explicitly project one run into batch-scoped search for analysis, but publishing accepted evaluation results into final matter coding remains a separate planned action.

## Analysis tasks and selected issue recommendations

A published Analysis Task can be run from the batch **Analysis** panel. The run pins that exact task version and stores an immutable Decision Result for each document. Published task versions cannot be edited. Select **Create draft revision** in the task workspace to start a new version with the same definition, then regenerate or edit its Decision Specification before publishing it.

Generated Decision Specifications include a frozen `decision_context` derived from the reviewed Task Definition. It summarizes the controlling guidance, responsiveness scope, inclusions, exclusions, issue definitions, entities, dates, terminology, and examples needed for the decision. The compiler also attaches every exact reviewed definition excerpt and its content hash as `source_material`, so the generated summary is not the provider's only source of matter guidance. Every document request sends this context to Jev as `matter.decision_context` alongside the document text, metadata, and paragraphs. Older specifications without embedded source material receive the complete pinned Task Definition as a runtime compatibility fallback; regenerate and publish a new task version to make the structured context directly reviewable.

For a multi-class issue question, the Decision Specification can use a `SELECTED_OPTION` recommendation. The question's field mapping explicitly lists which model options may become `issue_tag` values, and the policy sets the minimum selected-option probability. A mapped option that meets the threshold produces a recommendation containing the issue value and probability. An unmapped fallback such as `unclear`, or a selected option below the threshold, fails closed and does not recommend a tag.

Matched, field-mapped recommendations are also stored as typed values on the isolated analysis run. After the run completes, select **Make searchable** in the Analysis panel to choose that run as the batch's searchable coding source. A batch can expose only one selected run at a time. When projection finishes, a **Batch Coding** section appears with batch-only filters and facets for responsiveness, privilege, issue, or any other mapped field produced by that run.

This operation does not accept or publish the values as final matter tags. The database remains authoritative for every run, while OpenSearch contains a rebuildable, bounded projection identified by batch, selected run, field, value, and score. Ordinary matter search and metadata remain unchanged. Selecting a different completed run replaces only this batch's searchable coding projection.

## Current limitations

Keyword query batches and samples from Keyword saved searches are supported; semantic and hybrid result sets are not yet available for ordinary batch creation. Assessment retrieval can use all controlled search modes. Adjudication and publish-to-matter controls remain planned.
