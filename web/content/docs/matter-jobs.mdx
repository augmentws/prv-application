---
title: Matter jobs
description: Add large collection selections to a matter and follow durable background progress.
---

Matter jobs add collection documents and run durable document processing. The matter stores a link to each source collection item; the Artifact Service continues to own native files and derived artifacts.

The **Jobs** tab also shows bulk tag jobs started from matter search. Each row identifies the target field and value, the frozen query or filter scope, current status and progress, tagged and failed counts, and any available error. A snapshotted job with no completed document batches displays **Waiting** and **Waiting for capacity** until its first batch reports progress. Active bulk tag jobs refresh automatically, so you can close the original progress dialog and follow them here.

Matter **ADMIN** users can start and cancel these jobs. The source collection and destination matter must belong to the same client, and the matter must be active.

## Start from collection documents

1. Open a client's collection and stay on **Documents**.
2. Search or choose any facet filters you need. Leave them empty to select the entire collection.
3. Select **Add all matching**.
4. Choose an active destination matter and select **Start job**.

The application redirects to the matter's **Jobs** tab. The job freezes the matching IDs before processing, so an upload or metadata change made after that point does not silently change the running selection.

## Start from custodians

1. Open a collection's **Custodians** tab.
2. Select one or more custodians.
3. Select **Add documents to matter**, choose a matter, and start the job.

Documents associated with any selected custodian are included. A document associated with multiple selected custodians is added only once.

## Understand status and counts

- **Queued** means Core accepted the request and the workflow is waiting for a worker.
- **Snapshotting** means the current collection query is being frozen.
- **Running** means durable batches are adding matter links.
- **Completed** means every batch finished.
- **Failed** means processing stopped; the job detail shows the available error.
- **Canceled** means no further documents will be added by the job. Documents already added remain in the matter.

**Matched** is the frozen selection size. **Processed** is the number visited by completed batches. **Added** counts new matter links. **Already present** counts items that were previously linked by this or another job. Retrying or overlapping selections therefore does not duplicate matter documents.

During import, source custodian relationships are copied into Core-owned matter-document associations. The matter **Overview** uses those associations to show a distinct custodian count alongside the document count.

## Generate document embeddings

Open the matter's **Jobs** tab and select **Generate embeddings**. The job freezes the matter's current document list, then processes it in durable batches. Documents added after planning begins are handled by a later job.

For each document, Priv-View chooses extracted text first, then OCR text, then a supported text-based native file. It creates a sentence-aware chunk-set Parquet artifact and a matching vector-set Parquet artifact. Both artifacts remain associated with the source collection item and record their source lineage. Source reads, chunk preparation, and vector-artifact writes use bounded per-document concurrency, while chunks from multiple documents are embedded together up to the model service's input limit. Worker logs report preparation and completion progress every 25 documents, plus preparation, raw-inference, persistence, and total throughput after each batch. After every durable embedding batch finishes, the job updates the search index in one paged operation and performs one final refresh; the index stores chunks as nested records under the owning matter document.

The embedding job reports:

- **Generated** for documents that received a new vector set;
- **Skipped** for documents whose matching artifacts already exist or that have no usable text;
- **Chunks** for the total chunks represented by processed documents;
- **Failed** for individual documents that could not be processed.

Rerunning a job is safe. Priv-View reuses artifacts when the source content, chunking settings, model revision, dimensions, and normalization configuration match. Changing any of those inputs produces a distinct derivation without overwriting earlier artifacts.

When `EMBEDDING_PROVIDER=voyage_api`, newly created jobs use the configured hosted execution mode. The default real-time mode groups chunks into requests, runs multiple durable matter batches concurrently, enforces the configured Voyage TPM and RPM limits, and retries transient failures. Optional asynchronous Batch API mode persists provider identifiers, polls durably, and resumes result ingestion after worker restarts. Batch API mode requires provider billing and is enabled with `EMBEDDING_VOYAGE_BATCH_ENABLED=true`.

The embedding-job table reports external provider usage as the total token count, separate input and output token counts, and provider request count. These values are rolled up from the retry-safe provider usage ledger and update while the job runs.

## Cluster document topics

Topic clustering requires at least one completed embedding job with usable chunks. Open the matter's **Jobs** tab and select **Cluster topics**.

Choose an operating mode:

- **Automatic discovery** learns a natural topic count from the sample and can leave unrelated material unassigned.
- **Fixed topic count** creates the exact requested number of sample clusters. Use this when a predictable taxonomy size matters more than learning the natural count.

Both modes reduce embedding noise with PCA before clustering and keep their full-corpus assignment centroids in the original embedding space. Fixed mode runs MiniBatch K-means with the requested count. Automatic discovery evaluates bounded MiniBatch K-means candidates of 10, 20, 30, 40, and 50 topics, subject to the available sample and configured maximum, then selects the best-separated result while penalizing a solution dominated by one cluster. Generated names use terms that distinguish one cluster from the others and ignore common email-routing vocabulary.

**Sample chunks** controls how many chunk vectors are used to discover the clusters. It does not control the number of topics. Increasing the sample improves corpus coverage but uses more clustering time and memory. Blank and very short chunks are excluded, and exact duplicate chunk text is sampled only once. Long documents are capped and represented by chunks spaced across their eligible content so they do not dominate discovery.

Discovery does not immediately change metadata. When discovery finishes, the job enters **Awaiting review**. Select **Review topics** to open the job's dedicated review page and inspect the proposed names, keywords, sample sizes, and representative excerpts without placing the proposal set in a modal. You can rename a topic, revise its description, exclude it, or include or exclude the entire set. At least one topic must remain included before applying.

Select **Apply topics** only after the proposal set is ready. The approved set is recorded with the reviewing user and time, then assignment visits every document in the frozen job scope using durable batches. Closing the browser while the job is awaiting review or applying is safe.

**Replace existing topic values when approved** is selected by default. Each processed document receives a metadata `CLEAR` event followed by its newly assigned topics. The current values are replaced, while the complete metadata event history remains available. Clear the option to append newly discovered topics instead.

Applying an approved set automatically creates an active, facetable, multi-value `topics` enum field when the matter does not already have one. Discovery alone does not create the field. Application also creates an **Analysis** metadata group and places the field there. If `topics` already exists, it must be an active, asserted, multi-value enum. Stable enum keys identify included proposals even when their display names are similar.

Topic names are generated from the strongest terms in representative sample chunks. Renaming a proposal does not change its learned centroid. During assignment, every available chunk is compared with the approved topic centroids, and a document receives its strongest qualifying topics. Documents without a qualifying topic are counted as unassigned. Published values are written through the same metadata ledger and search-projection path as other agent-authored metadata, so they are searchable and facetable after their batch finishes.

## Reliability and cleanup

Jobs use a durable workflow worker and can resume after an application or worker restart. Import selections are removed after their deterministic batches have been durably queued. Embedding and topic jobs retain compact batch snapshots containing the document IDs so their scope cannot drift. Core job records remain available for progress and audit history.

The **Jobs** tab refreshes while work is active; it is safe to close the browser. Canceling is best effort for work already executing, so the final added count can include a batch that completed at the same time as the cancellation request.

The Core API terminal shows repeated job-list requests while the Jobs tab is open.
Those requests only refresh the displayed status. Model loading, sampling, topic
discovery, batch counts, document failures, and completion are reported in the
separate workflow-worker terminal. The first embedding batch can take longer while
the configured model loads; later batches reuse the loaded model.

## Current limitations

The worker process must be running; otherwise an accepted job remains queued. After
an embedding-library or model-configuration change, restart the worker before
starting a new job. A job that already recorded document failures should be canceled
and rerun after correcting the cause; the rerun safely reuses any artifacts that were
successfully created. Embedding generation currently works only when a document has
extracted text, OCR text, or a supported text-based native artifact. Dense vectors
are indexed for semantic and hybrid search. Topic names currently use extractive
keywords rather than generative model labeling. Topic review supports renaming and
excluding proposals; it does not currently support merging clusters or adding a new
topic without rerunning discovery. A new run creates a new set of
stable topic values rather than merging equivalent topics across runs. Image-only
and unsupported binary documents require an extraction or OCR workflow first.
