title: Matter jobs
description: Follow durable imports, embeddings, topic processing, classification analysis, and other matter work.

Matter jobs add collection documents and run durable document processing. The matter stores a link to each source collection item; the Artifact Service continues to own native files and derived artifacts.

Open **Jobs** in the matter menu. Each job type has its own page: bulk tagging, document embeddings, topic clustering, document imports, question answering, classification analysis, and search exports. Select a type in the row at the top of the page. **Jobs** opens on **Document imports**. Because each type has its own address, the browser's Back button returns to the type you were on, and you can bookmark a type. Opening a specific document-import job opens **Document imports** with that job's details; following **Open job** from a classification run opens **Classification analysis** with that run's results, and Back closes them.

**Bulk tagging** shows bulk tag jobs started from matter search. Each row identifies the target field and value, the frozen query or filter scope, current status and progress, tagged and failed counts, and any available error. A snapshotted job with no completed document batches displays **Waiting** and **Waiting for capacity** until its first batch reports progress. Active bulk tag jobs refresh automatically, so you can close the original progress dialog and follow them here.

Matter **ADMIN** users can start this work and can cancel a job when its row offers that action. The source collection and destination matter must belong to the same client, and the matter must be active.

## Start from collection documents

1. Open a client's collection and stay on **Documents**.
2. Search or choose any facet filters you need. Leave them empty to select the entire collection.
3. Select **Add all matching**.
4. Choose an active destination matter and select **Start job**.

The application opens **Document imports** under the matter's **Jobs**. The job freezes the matching IDs before processing, so an upload or metadata change made after that point does not silently change the running selection.

Every publication job has a durable execution attempt. The Jobs table shows
the current execution stage and attempt number, while the progress bar uses
the frozen selection size and the count committed by completed publication
batches. Loading the job reconciles those counters from its durable batches
and reconciles a terminal DBOS outcome if a worker stopped before updating the
parent job record.

## Start from custodians

1. Open a collection's **Custodians** tab.
2. Select one or more custodians.
3. Select **Add documents to matter**, choose a matter, and start the job.

Documents associated with any selected custodian are included. A document associated with multiple selected custodians is added only once.

## Understand status and counts

- **Queued** means Core accepted the request and the workflow is waiting for a worker.
- **Snapshotting** means the current collection query is being frozen.
- **Running** means durable batches are adding matter links.
- **Completed** means every batch finished.
- **Failed** means processing stopped; the job detail shows the available error.
- **Canceled** means no further documents will be added by the job. Documents already added remain in the matter.

**Matched** is the frozen selection size. **Processed** is the number visited by completed batches. **Added** counts new matter links. **Already present** counts items that were previously linked by this or another job. Retrying or overlapping selections therefore does not duplicate matter documents.

During import, source custodian relationships are copied into Core-owned matter-document associations. The matter **Overview** uses those associations to show a distinct custodian count alongside the document count.

For matters with the standard **Email Domain** system field, newly added or republished documents receive their unique normalized From/To/CC/BCC domains through the normal `DOCUMENT_UPSERT` search projection. Document publication does not install or upgrade search-derived system fields. A full index rebuild is the lifecycle boundary that installs a missing Email Domain definition for an older matter and derives the field for the complete matter population.

## Publish unmapped metadata as matter labels

Collection items can contain external fields in `unmapped_metadata`, such as coding columns supplied by a load file. When documents are published to a matter, Priv-View compares those external keys with the matter's active asserted metadata definitions. A case-insensitive key match publishes the external value through the normal matter metadata ledger with source **Import**.

For example, if a collection item contains `tr2016_facets` and the destination matter has an active field whose key is `tr2016_facets`, each valid imported value becomes a matter label. Single-value fields create one imported `SET`; multi-value fields create one imported `ADD` per distinct value. Values must satisfy the destination field's type, cardinality, and allowed enum options. Unknown fields remain unmapped, empty values create no label, and invalid values are counted as import warnings.

Imported labels are not a separate projection. They appear in document coding history with source **Import** and participate in the field's existing confirmation and resolution policies. Search is updated from the resolved current value after the import batch commits.

Publishing is retry-safe. Each imported value receives a deterministic source identity based on the collection item and field, so retrying a batch or publishing the same item again does not append duplicate labels. Republishing also reconciles existing matter documents, which allows an older matter to receive labels that were not published by an earlier version of the workflow.

Document-import status distinguishes matter links from label publication: **Added** and **Already present** describe document links, while the imported-label counters report affected documents, events created, and invalid-value warnings. A missing external value is implicit and does not create a placeholder label or warning.

## Generate document embeddings

Open **Jobs** in the matter menu, select **Document embeddings**, then select **Generate embeddings**. The job freezes the matter's current document list, then processes it in durable batches. Documents added after planning begins are handled by a later job.

For each document, Priv-View chooses extracted text first, then OCR text, then a supported text-based native file. The embedding input places a non-empty email subject and original filename before that body text so semantic retrieval can use those high-signal descriptions. Sender and recipient headers are not embedded; they remain available to keyword search and exact filtering. Priv-View creates a sentence-aware chunk-set Parquet artifact and a matching vector-set Parquet artifact. Both artifacts remain associated with the source collection item and record their source lineage. Source reads, chunk preparation, and vector-artifact writes use bounded per-document concurrency, while chunks from multiple documents are embedded together up to the model service's input limit. Worker logs report preparation and completion progress every 25 documents, plus preparation, raw-inference, persistence, and total throughput after each batch. After every durable embedding batch finishes, the job updates the search index in one paged operation and performs one final refresh; the index stores chunks as nested records under the owning matter document.

The embedding job reports:

- **Generated** for documents that received a new vector set;
- **Reused** when a compatible vector set already existed and no inference was needed;
- **Skipped** only when a document had no supported or usable text;
- **Chunks** for the total chunks represented by processed documents;
- **Failed** for individual documents that could not be processed.

For newly planned jobs, select **View outcomes** from the job row to inspect the
complete document-level manifest. The viewer separates generated, reused, skipped,
failed, excluded, and canceled documents; shows stable reason codes; filters by
status or reason; links back to each authorized document; and downloads the full
manifest as CSV or Parquet. The same outcome viewer is available beside the selected
embedding set on the **Classifiers** page.

Core stores one small manifest record for the logical job. The Artifact Service owns
the compressed Parquet rows, with exactly one row per frozen document, so complete
diagnostics do not add one Core database row per document. Each durable batch first
publishes an immutable outcome fragment, and job completion verifies and combines
all fragments before the job becomes complete. Cancellation retains finished batch
outcomes and records uncompleted documents as **Canceled** when a planned manifest
exists.

Jobs completed before document outcomes were introduced retain their existing
aggregate totals and bounded error text. Their outcome viewer explicitly labels the
details as unavailable instead of attempting to reconstruct document identities or
reasons that were never stored.

The displayed document and chunk counts are reconciled from the job's durable batch records whenever the job is loaded. If a worker interruption leaves the application record active after its durable workflow has already succeeded, failed, or been canceled, loading the job reconciles that terminal state and stops unnecessary status polling. Canceling a job also reports the latest completed batch totals rather than the last progress snapshot written by the parent workflow.

Rerunning a job is safe. Priv-View reuses artifacts when the source content, subject, filename, embedding-input format, chunking settings, model revision, dimensions, and normalization configuration match. Changing any of those inputs produces a distinct derivation without overwriting earlier artifacts.

When `EMBEDDING_PROVIDER=voyage_api`, newly created jobs use the configured hosted execution mode. The default real-time mode groups chunks into requests, runs multiple durable matter batches concurrently, enforces the configured Voyage TPM and RPM limits, and retries transient failures. Optional asynchronous Batch API mode persists provider identifiers, polls durably, and resumes result ingestion after worker restarts. Batch API mode requires provider billing and is enabled with `EMBEDDING_VOYAGE_BATCH_ENABLED=true`.

The embedding-job table reports external provider usage as the total token count, separate input and output token counts, and provider request count. These values are rolled up from the retry-safe provider usage ledger and update while the job runs.

## Cluster document topics

Topic clustering requires at least one completed embedding job with usable chunks. Open **Jobs** in the matter menu, select **Topic clustering**, then select **Cluster topics**.

Choose an operating mode:

- **Automatic discovery** learns a natural topic count from the sample and can leave unrelated material unassigned.
- **Fixed topic count** creates the exact requested number of sample clusters. Use this when a predictable taxonomy size matters more than learning the natural count.

Choose a document scope:

- **Entire matter** analyzes every document with usable embeddings.
- **Include only a saved search** analyzes only documents matched by the selected saved search.
- **Entire matter excluding a saved search** analyzes the matter except for documents matched by the selected saved search. This is useful for removing form email, newsletters, and other known noise from topic discovery.

Saved-search scopes currently support Keyword saved searches so the complete matching set can be enumerated. Priv-View snapshots the search definition and current physical search index when the job is created, so later saved-search edits or deletion do not change the run. The selected scope controls both topic discovery and full-corpus topic assignment. With an exclusion scope, excluded documents are not sampled or assigned by that run; any topic values they already have remain unchanged.

Both modes reduce embedding noise with PCA before clustering and keep their full-corpus assignment centroids in the original embedding space. Fixed mode runs MiniBatch K-means with the requested count. Automatic discovery evaluates bounded MiniBatch K-means candidates of 10, 20, 30, 40, and 50 topics, subject to the available sample and configured maximum, then selects the best-separated result while penalizing a solution dominated by one cluster. Generated names use terms that distinguish one cluster from the others and ignore common email-routing vocabulary.

**Sample chunks** controls how many chunk vectors are used to discover the clusters. It does not control the number of topics. Increasing the sample improves corpus coverage but uses more clustering time and memory. Blank and very short chunks are excluded, and exact duplicate chunk text is sampled only once. Long documents are capped and represented by chunks spaced across their eligible content so they do not dominate discovery.

Discovery does not immediately change metadata. When discovery finishes, the job enters **Awaiting review**. Select **Review topics** to open the job's dedicated review page and inspect the proposed names, keywords, sample sizes, and representative excerpts without placing the proposal set in a modal. You can rename a topic, revise its description, exclude it, or include or exclude the entire set. At least one topic must remain included before applying.

After a run leaves **Awaiting review**, the Jobs table keeps a **View topics** action whenever that run retained proposals. The historical page is read-only and shows the saved names, descriptions, keywords, excerpts, and inclusion decisions.

When starting discovery, choose where the approved values will be stored. The destination is fixed for that run and shown again on the review page:

- **Use Topics field** uses the standard `topics` field and creates it when necessary.
- **Choose an existing field** adds the approved topics to an existing field's allowed values. Only active, asserted, multi-value enum fields are available because a document can receive more than one topic.
- **Create a new field** creates a facetable, multi-value enum in the Analysis group using the name and key you provide.

Select **Apply topics** only after the proposal set is ready. The approved set, destination field, reviewing user, and review time are recorded, then assignment visits every document in the frozen job scope using durable batches. Closing the browser while the job is awaiting review or applying is safe.

Assignment batches run concurrently. After all assignments are durable, one checkpointed search-projection pass updates OpenSearch for the frozen document scope. This avoids serializing every assignment batch behind a separate index refresh. Operators can tune assignment parallelism with `MATTER_TOPIC_ASSIGNMENT_CONCURRENCY`; the default is `8`.

**Replace existing values in the destination field when approved** is selected by default. Each processed document receives a metadata `CLEAR` event followed by its newly assigned topics. The current destination-field values are replaced, while the complete metadata event history remains available. Clear the option to append newly discovered topics instead.

Discovery alone does not create or modify a metadata field. When the selected destination must be created, application also creates an **Analysis** metadata group when necessary and places the field there. Stable enum keys identify included proposals even when their display names are similar.

Topic names are generated from the strongest terms in representative sample chunks. Renaming a proposal does not change its learned centroid. During assignment, every available chunk is compared with the approved topic centroids, and a document receives its strongest qualifying topics. Documents without a qualifying topic are counted as unassigned. Published values are written through the same metadata ledger and search-projection path as other agent-authored metadata, so they are searchable and facetable after their batch finishes.

## Run classification analysis

Create and start classifier-backed work from **Analysis tasks** in the matter menu. The Analysis Task is the reusable definition: it pins the approved model version and destination field and lets an administrator select either a ready review batch or the whole matter. Prediction output does not live on the task definition.

Every execution appears on the **Classification analysis** page of **Jobs**. Each row identifies the task and whether it used a review batch or the whole matter, displays its durable stage, attempt, progress, and frozen document count, and provides the available cancel or retry action. Select **View job**, or follow **Open job** from the task's compact run history, to review the execution.

The job result contains:

- the frozen population and selected scope;
- feature-ready, feature-missing, and feature-failed counts;
- evaluated, abstained, excluded, and failed scoring counts;
- the model's pinned prediction policy and version provenance; and
- a per-class prediction chart derived from the immutable prediction artifact.

The class chart initially shows the model's resolved predictions. Use its probability selector to recalculate counts at a minimum such as **Probability ≥ 80%**. The threshold is inclusive. For a multi-label one-vs-rest model, every class at or above the selected probability counts, so a document can contribute to more than one class. Documents for which no class reaches the selected threshold are reported as evaluated with no prediction. Changing this control is read-only: it neither reruns scoring nor changes the destination coding field.

Batch- and whole-matter scopes use the same job-result view. A whole-matter classification run evaluates its Artifact-backed frozen population without creating one review-batch membership row per document. Both scopes keep predictions as isolated analysis output and do not update the destination coding field. Creating searchable batch coding or changing matter coding remains a separate, explicit operation.

## Run question answering

Question-answering Analysis Tasks run against a ready review batch from the batch review workspace. Every accepted run appears on the **Question answering** page of the matter's **Jobs**, whether it uses the Jev provider or OpenAI Decisions.

Each row shows the pinned task version, review batch, provider and model, durable status, attempt, and document progress. Select **Open batch** to inspect the run's document-level answers and evidence. Results remain isolated batch output until a matter administrator explicitly publishes the configured destination fields.

Question answering currently uses review-batch scope. The Jobs view is for monitoring, canceling an active run, locating output, and inspecting document failures; starting a run still happens from the review batch after the task version is published. Select the batch name to open that batch. When a run finishes with document failures, select its **Completed with errors** status to open the failure dialog. The dialog shows each failed document, its stable failure code, the retained human-readable reason, the execution attempt, and whether the failure is safe to retry; the Jobs row does not repeat that diagnostic text.

Retry either selected retryable documents or every retryable failure. A retry creates a new durable execution attempt for the same logical run and frozen batch, and schedules only the chosen failed documents. Previously successful documents and their isolated results are not evaluated again. Non-retryable failures remain visible for correction or investigation. Historical runs created before per-document diagnostics were added identify the affected documents but may report that their original reason is unavailable. Those unknown legacy failures are retryable because the isolated analysis workflow can safely rerun them without changing successful document results.

The active run can also be canceled from the batch Analysis panel. Cancellation stops the durable parent workflow and its document child workflows, preserves completed and failed results, and marks documents that had not finished as skipped.

OpenAI Decisions tasks require `OPENAI_API_KEY` in the API and worker environment. The API checks this before creating the batch run so a missing provider credential cannot fan out into one failure per document.

## Export search results

Start a search export from **Search & Review → Export results**, then follow the export on the **Search exports** page of the matter's **Jobs**, which opens when the export starts. Each row shows the requested filename, selected column count, creator, durable stage, exported rows over matched rows, output size, expiration, and available actions.

- **Preparing** reauthorizes the initiating user and resolves the frozen field and index contract.
- **Exporting** reads the pinned OpenSearch generation through one point-in-time snapshot and updates document progress after every page.
- **Uploading** publishes the complete CSV to the Artifact Service.
- **Completed** enables **Download CSV** after another current-access check.
- **Failed** shows the retained reason and offers **Retry** when the dependency failure is transient and the pinned index generation is still retained.
- **Canceled** means no CSV was published. A later retry starts the deterministic export again from the beginning.

Search export retries create a new common job execution attempt while retaining the original frozen query, ordered field contract, CSV policy, and physical index generation. Core does not create one database row per exported document, and CSV bytes are never stored in the Core database. The Artifact Service inventory is the authoritative list of immutable output files for the matter; the Core job is the control and audit record.

## Reliability and cleanup

Jobs use a durable workflow worker and can resume after an application or worker restart. Import selections are removed after their deterministic batches have been durably queued. Document-import and embedding jobs retain a common execution attempt with stage, progress, heartbeat, cancellation, structured failure, and attempt history. Embedding and topic jobs retain compact batch snapshots containing the document IDs so their scope cannot drift. New embedding jobs additionally retain an Artifact-backed document-outcome manifest. Core job records remain available for progress and audit history.

Users with **Delete jobs** permission can delete a completed, completed-with-errors, failed, or canceled job from its row action menu. Active work must be canceled or allowed to complete first. Job deletion is soft: the logical job disappears from the normal Jobs lists while its domain record, execution attempts, document failures, outputs, artifacts, and audit history remain intact. This operation does not delete documents or reverse coding that the job already published.

Job pages refresh while work is active; it is safe to close the browser. Canceling is best effort for work already executing, so the final added count can include a batch that completed at the same time as the cancellation request.

The Core API terminal shows repeated job-list requests while a Jobs page is open.
Those requests only refresh the displayed status. Model loading, sampling, topic
discovery, batch counts, document failures, and completion are reported in the
separate workflow-worker terminal. The first embedding batch can take longer while
the configured model loads; later batches reuse the loaded model.

## Current limitations

The worker process must be running; otherwise an accepted job remains queued. After
an embedding-library or model-configuration change, restart the worker before
starting a new job. A job that already recorded document failures should be canceled
and rerun after correcting the cause; the rerun safely reuses any artifacts that were
successfully created. Embedding generation currently works only when a document has
extracted text, OCR text, or a supported text-based native artifact. Dense vectors
are indexed for semantic and hybrid search. Topic names currently use extractive
keywords rather than generative model labeling. Topic review supports renaming and
excluding proposals; it does not currently support merging clusters or adding a new
topic without rerunning discovery. A new run creates a new set of
stable topic values rather than merging equivalent topics across runs. Image-only
and unsupported binary documents require an extraction or OCR workflow first.
