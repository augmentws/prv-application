---
title: Metadata definitions
description: Configure the fields that a matter will use for search, review, filtering, and agent output.
---

A metadata definition describes a field available within one matter. Every new matter receives the current versioned **edrm-core** default profile. Definitions provide the schema for immutable document-value events and their resolved current values.

## Default matter profile

Matter creation automatically adds 29 definitions covering:

- identification, including control number, original filename, and document title;
- family, direct parent/child, and custodian relationships;
- source path, a canonical document date, and source-system timestamps;
- email sender, recipients, unique participant domains, subject, sent date, and received date;
- file extension, size, page count, MD5, and SHA-256; and
- responsiveness, privilege, key-document coding, and review notes.

The **Source** column identifies how values will be supplied:

- **System** fields resolve from Priv-View relationships or derived Core state. Custodian, Family ID, Parent ID, and Child ID are mandatory system fields.
- **Imported** fields come from the promoted collection item and retain source provenance.
- **Asserted** fields accept reviewer assertions through the Core API and are ready for later agent assertions through the same command service.

The profile is copied into the matter as ordinary database rows, so later matter-specific configuration does not mutate the application template or another matter.

### Family relationships

**Family ID** groups the complete document family. **Parent ID** and **Child ID** describe only direct edges: a child has at most one Parent ID, while a parent may have multiple Child IDs. These values use the same source control-number precedence as Control number, falling back to the collection source-item ID. Internal collection-item UUIDs remain the authoritative relationship keys and are not shown as Parent ID or Child ID.

Relationships are established during collection ingestion. Sharing a Family ID alone does not identify a parent, so Priv-View does not guess parent/child edges for family-only source data.

### File date and source dates

**File date** is the normalized date intended for consistent chronology, filtering, and review. The Artifact Service calculates it when a collection item is created: an email uses its sent date, an attachment inherits its parent email's File date, and a standalone file uses Source modified at. If the applicable source timestamp is absent, File date is empty.

**Source created at** and **Source modified at** preserve timestamps reported by the original source or importer. They do not represent when Priv-View collected, published, indexed, or coded the document. Source formats may omit them or provide only one timestamp; for example, a ZIP entry may supply the same available timestamp for both fields.

The collection item remains authoritative for all three values. Publishing or rebuilding a matter copies them into the matter search projection without changing the stored collection values.

New matters receive File date automatically. When an older matter does not have the definition, confirming a full search-index rebuild installs File date in the Source Dates group before rebuilding the document projections.

### Email Domain

**Email Domain** is a read-only, multi-value system field. For each document, Priv-View parses the structured From, To, CC, and BCC participants, lowercases and IDNA-normalizes their domains, removes duplicates, and sorts the result. A non-email document or an email without a usable address has zero values; Priv-View does not write a synthetic **No value** tag.

New matters receive the field automatically and populate it during normal indexing. A full search-index rebuild installs a missing Email Domain definition and Email-group membership for a matter created from an older profile, then derives the field while rebuilding every document projection. Publishing documents does not perform this profile upgrade. Rebuilding the index is also the supported way to refresh this derived field across the complete matter.

## Add a field

1. Open a client, then open a matter.
2. Select **Metadata fields** in the matter menu, then **Definitions**.
3. Select **Add field**.
4. Enter a display name and stable field key.
5. Choose the value type and cardinality.
6. Configure field behavior and create the field.

Field keys use lowercase letters, numbers, and underscores and must begin with a letter. Treat the key as a stable machine-facing identifier; use the display name for human-readable wording.

## Value types

| Type | Use |
| --- | --- |
| Text | Short text and identifiers whose formatting must be preserved. |
| Long text | Larger bodies of text that should not be used as facets. |
| Integer | Signed whole numbers backed by a 64-bit integer. |
| Decimal | Floating-point numeric values. Do not use it when exact fixed-precision arithmetic is required. |
| Boolean | True or false values. |
| Date | Calendar dates without a time of day. |
| Datetime | A date and time. |
| Enum | One or more values from a controlled option list. |
| JSON | Structured data that does not fit a simpler type. |

Numeric identifiers that contain non-numeric characters, preserve leading zeroes, or have significant formatting should use **Text**, not Integer or Decimal.

## Document values and history

Asserted document metadata does not add a database column for every matter field. The Core API stores each change as an immutable event tied to a matter document and that matter's field definition. A separate current-value projection is resolved from those events for efficient reads and search indexing.

Supported operations are:

- **Set** and **Clear** for single-valued fields;
- **Add**, **Remove**, and **Clear** for multi-valued fields; and
- **Confirm** and **Reject** for reviewing an earlier assertion.

The field's assertion and resolution policies determine whether a new assertion is immediately effective, pending confirmation, or conflicting with another assertion. Events retain their actor, source, confidence, relationships, and creation time even after they stop contributing to the current value.

Every write uses one Core transaction to append the event, recompute the affected field projection, add its audit entry, and create a durable search-refresh operation. This is application behavior rather than a database trigger. Search refresh can finish asynchronously; the Core event ledger and current projection remain authoritative.

The current-value and history APIs are:

```text
GET  /v1/matters/{matter_id}/documents/{document_id}/metadata-values
GET  /v1/matters/{matter_id}/documents/{document_id}/metadata-values/{definition_id}
GET  /v1/matters/{matter_id}/documents/{document_id}/metadata-values/{definition_id}/events
POST /v1/matters/{matter_id}/documents/{document_id}/metadata-values/{definition_id}/events
```

System and imported fields are read-only through this event API because their authoritative values come from Core relationships or the promoted collection item. Browser-based document coding controls are still planned; the current implementation exposes the complete storage and API foundation.

## Cardinality

- **Single value** allows one current value for the field.
- **Multiple values** allows a set of values.

## Behavior settings

- **Searchable** makes the field eligible for future search operations.
- **Available as a filter** makes the field eligible for faceting. Long text and JSON cannot be faceted.
- **Visible to reviewers** marks the field for reviewer-facing experiences.
- **Agents may assign values** makes an active, matter-owned Asserted field available as an output destination for analysis tasks. Select **Edit**, change the setting in the field modal, and save to update it later. The same modal manages controlled Enum values. System and Imported definitions cannot be AI-assignment destinations because their values are owned by another source.

For imported collection metadata that already carries a path, create a **Text** field and enable **Interpret delimited values as a hierarchy** under **Hierarchy paths**. Enter `/` as the hierarchy delimiter. Enabling the option also enables **Searchable** and **Available as a filter**. For example, `/` interprets these source values as a hierarchy:

```text
Initiatives/344
Initiatives/344/Workstream A
Archive/2025
```

The source value remains unchanged. During search indexing, Priv-View also projects each prefix: `Initiatives`, `Initiatives/344`, and `Initiatives/344/Workstream A`. This lets a parent filter include every descendant without creating enum options from collection data. Empty path segments, paths deeper than 32 levels, segments longer than 200 characters, and complete paths longer than 4,096 characters are rejected during projection. Whitespace around each segment is removed in the hierarchy projection.

For Enum fields, enter one option per line as `stable_key | Display label`. To create a hierarchy, add the stable key of the parent as a third value and list parents before their children:

```text
legal | Legal
contracts | Contracts | legal
nda | NDAs | contracts
```

The parent relationship is immutable after an option is created. Labels and descriptions may still change. A parent cannot be deactivated while it has active children; deactivate its children first. Hierarchical enum fields must also be marked **Available as a filter** to appear as drill-down facets in Search & Review.

The Matter Definition setup agent can also propose creation or configuration changes for matter-owned **Asserted** fields. Each proposal requires an authorized matter administrator to approve it before execution. Enum keys remain stable: the agent may add a value, update its label or description, or deactivate it, but does not delete historical values. System and Imported definitions are not editable through these tools.

## Metadata groups

Select **Metadata fields** in the matter menu, then **Groups**, to see the seven standard groups. The initial table/document visibility is:

| Group | Results table | Document view |
| --- | --- | --- |
| Identification | Shown | Shown |
| Family | Shown | Shown |
| Custodian & Source | Shown | Shown |
| Email | Hidden | Shown |
| File Details | Hidden | Shown |
| Source Dates | Hidden | Shown |
| Review Coding | Shown | Shown |

Use the **Table** and **Document** controls on a group to save your own visibility choices. Your preference overrides the matter default without changing what another user sees.

Select **Create group** to collect existing fields into either:

- a personal group visible only to you; or
- a matter group available to everyone who can access the matter.

Personal groups and personal visibility preferences are never included in templates or clones. Matter groups, field order, and default visibility are included.

### Filter organization

Search & Review and the batch review workspace use active metadata groups to organize their filter panels. Groups follow their configured sort order, and fields inside each group follow the order in the group's definition. Only active definitions that are configured for search and filtering appear.

Select a group heading to collapse or expand all of its field filters. Groups start expanded, and a group with active selections shows their count in its heading so those selections remain visible when the group is collapsed.

If a field belongs to more than one active group, the first group in configured order owns that filter so the same control is not repeated. Filterable fields that do not belong to an active group remain available under **Matter metadata**. Search & Review also places its virtual **Coded by** filter under **Document fields**. Batch-specific topic and Batch Coding filters remain in their own sections above the matter metadata groups.

The **Table** and **Document** visibility controls affect their named result and document surfaces; they do not remove a field from the filter panel. Archive or suspend a group, or change a definition's search/filter settings, when it should no longer organize an available filter.
