# Topic Clustering Experiments and Outcomes

## Purpose

This document records the topic-clustering approaches tried against the current Priv-View corpus, their observed outcomes, and the conclusions that shaped the current implementation. It is an engineering retrospective, not a claim that automatic topic discovery is complete.

The goal is to discover a useful set of named, matter-level topics from document embeddings, let a matter administrator review those topics, and only then apply approved topic values to all documents in the matter.

## Current status

New topic jobs use clustering version 3:

1. Sample eligible, de-duplicated chunks.
2. Normalize their existing embedding vectors.
3. Reduce the vectors with PCA.
4. In automatic mode, compare several MiniBatchKMeans cluster counts and select the best scored candidate.
5. Generate extractive names from terms that distinguish each cluster from the other clusters.
6. Stop at `AWAITING_REVIEW` so a user can rename, describe, exclude, and approve proposals.
7. After approval, assign up to the configured number of topics to every eligible document and update the search projection.

This version produces more useful structure than the earlier density-based implementations, but it does not yet produce a consistently clean, human-quality topic taxonomy. Topic review remains a required product boundary.

## Test corpus and baseline

The principal investigation used an Enron-derived matter containing approximately 55,366 documents. Repeat comparisons used the same deterministic sample of 10,000 eligible chunks whenever possible.

The vectors were generated by the configured `voyageai/voyage-4-nano` model with 1,024 dimensions and normalization enabled. The comparisons therefore tested clustering and sampling changes against the same underlying embedding source rather than changing the embedding model at the same time.

Sampling is used only to discover candidate topics. It does not define the final document population. After the proposals are approved, assignment evaluates the documents in the frozen matter scope using centroids stored in the original normalized embedding space.

## Summary of experiments

| Version or change | Discovery method | Observed result | Outcome |
| --- | --- | --- | --- |
| Version 1 automatic | Gaussian random projection and HDBSCAN | One cluster of about 200 calendar-like chunks; roughly 9,800 sampled chunks treated as noise | Failed to discover the corpus structure |
| Input and sampling cleanup | Better normalized text, short-chunk filtering, exact duplicate suppression, and even sampling within long documents | Automatic discovery still returned one topic | Improved inputs, but did not solve the clustering failure |
| Version 2 automatic | PCA, UMAP, and HDBSCAN | Three clusters: approximately 283 calendar, 8,622 general email/routing, and 675 web/image chunks | Fixed the literal one-topic result, but found format and template classes rather than useful subjects |
| Fixed 30-topic comparison | PCA and MiniBatchKMeans with 30 requested clusters | Mixture of recognizable business subjects and junk/template clusters | Demonstrated that the embeddings contain semantic signal and that partitioning was more productive than density discovery |
| Version 3 automatic | PCA and candidate MiniBatchKMeans scored by separation and cluster dominance | Selected 50 topics; surfaced real themes but also many narrow, template, and noisy topics | Current implementation; materially better exploration, but still requires review and tuning |

## Experiment 1: random projection and HDBSCAN

The first automatic implementation normalized the sampled embeddings, reduced them to at most 50 dimensions with `GaussianRandomProjection`, and ran HDBSCAN. The minimum cluster size was derived from the sample size and the maximum topic count. `allow_single_cluster` was enabled, and an empty discovery could fall back to a single cluster.

On the 10,000-chunk sample, HDBSCAN produced one dense cluster containing about 200 chunks. Approximately 9,800 chunks were classified as noise. The generated name was similar to `Description · Time · Calendar Entry`.

The important detail is that the algorithm did not combine all sampled content into one coherent subject. It found one repetitive calendar/template pattern and rejected almost everything else. The UI exposed that as one topic, which made the result look like a single-topic corpus even though most of the sample was unassigned noise.

### Conclusion

Density clustering was too conservative and too sensitive to repeated formatting patterns for this heterogeneous email corpus. A one-cluster fallback also hid the difference between a genuinely coherent corpus and a failed discovery.

## Input cleanup and sampling changes

Before replacing the clustering algorithm, the inputs and sampling behavior were improved.

### Collection text processing

The collection-level text processor was iterated through several versions to remove recognized email transport wrappers and attachment placeholders while preserving substantive forwarded content. The later rules handle multiple Lotus Notes forwarding-marker variants, split marker dates, calendar forwarding, and cases that previously removed subjects or entire messages.

These changes affect topic discovery only after a new collection processing run and a new embedding job have produced artifacts from the active normalized text. Existing embedding and topic jobs are immutable snapshots and do not silently adopt newer processed text.

### Sampling changes

The topic sampler was changed to:

- Exclude blank chunks and normalized text shorter than 80 characters.
- Suppress exact duplicate chunks across the matter using a case-insensitive, whitespace-normalized SHA-256 key.
- Choose evenly spaced eligible chunks from long documents instead of arbitrary chunks.
- Retain the deterministic document shuffle and fixed random seed so comparable reruns use a stable sample.
- Keep a per-document cap so a few long documents cannot consume the entire sample.

The sample remains a chunk sample rather than a document sample. Assignment after approval still evaluates the full frozen document scope.

### Outcome

These changes removed obvious duplicate and low-information inputs, but automatic HDBSCAN still found only one useful dense group. That result showed that input cleanup was necessary but not sufficient; the discovery model itself was the main limitation.

## Experiment 2: PCA, UMAP, and HDBSCAN

Clustering version 2 replaced random projection with PCA and used UMAP before automatic density clustering:

- PCA reduced normalized vectors to at most 50 dimensions.
- UMAP reduced the automatic-mode representation to at most 10 dimensions using cosine distance, 15 neighbors, zero minimum distance, and deterministic settings.
- HDBSCAN ran in UMAP space with `allow_single_cluster` disabled.
- Automatic discovery failed rather than publishing when fewer than two topics survived.
- Fixed mode used MiniBatchKMeans in PCA space.
- Final proposal centroids continued to be calculated in the original 1,024-dimensional normalized space.

On the same 10,000-chunk sample, version 2 produced three clusters:

- About 283 chunks named around `Description · Time · Calendar Entry`.
- About 8,622 chunks named around `Enron · Ect · Thanks`.
- About 675 chunks named around `Com · Image · Http`.

### Conclusion

Version 2 eliminated the literal one-topic outcome, but the three clusters represented calendar formatting, generic email/routing language, and web/image material. The largest cluster contained about 86% of the sample. The algorithm was organizing the corpus principally by document format, repetition, and local vector density—not by the business or legal subjects a reviewer would expect.

Counting clusters was therefore an inadequate success measure. Three unusable topics were not an improvement in product terms over one unusable topic.

## Fixed-count KMeans comparison

A fixed 30-topic MiniBatchKMeans run was inspected to determine whether the embedding vectors themselves lacked useful semantic information.

The run produced recognizable subject groups including:

- Scheduled outages.
- Training.
- Master power agreements.
- NYISO markets.
- Gas and Transwestern material.
- Management summaries and hot lists.
- Reports, expenses, and validation.
- Retention plans.

It also produced clusters dominated by routing terms, names, HTML, image references, spam, and repeated templates.

### Conclusion

The embeddings contain meaningful semantic signal. The earlier one-topic behavior was not enough evidence to conclude that the embedding model was bad. A partitioning model forced the sample into groups and exposed more of that signal, although cluster membership and naming still contained substantial noise.

This comparison motivated moving automatic mode away from HDBSCAN and toward evaluated KMeans candidates.

## Experiment 3: candidate KMeans automatic mode

Clustering version 3 uses PCA for both modes.

Fixed mode runs MiniBatchKMeans with the requested count and verifies that the requested number of distinct clusters was produced.

Automatic mode:

1. Builds valid candidates from 10, 20, 30, 40, and 50 topics, bounded by the configured maximum, the number of distinct sample points, and a minimum average of five sampled points per cluster.
2. Fits MiniBatchKMeans for each candidate.
3. Evaluates a deterministic subsample of at most 2,000 vectors.
4. Calculates the Euclidean silhouette score in PCA space.
5. Applies a penalty when the largest cluster exceeds 25% of the sample.
6. Selects the candidate with the highest combined score.

The score is:

```text
silhouette_score - max(0, largest_cluster_fraction - 0.25)
```

Version 3 also changed naming. Rather than extracting common terms independently from every cluster, it builds cluster-level TF-IDF features intended to emphasize terms that distinguish one cluster from the others. Common routing and formatting terms such as `bcc`, `cc`, `com`, `ect`, `email`, `enron`, `hou`, `http`, `mailto`, `subject`, `thank`, `thanks`, and `www` are ignored.

### Outcome

On the same 10,000-chunk corpus sample, automatic mode selected 50 topics. It found several recognizable themes such as scheduled outages, master power agreements, NYISO reserves, retention plans, training, management summaries, and gas-related material.

It also created many narrow or low-value clusters driven by individual names, uncommon phrases, HTML/marketing content, or repeated templates. Examples included names similar to `Carrfut Research`, `Mba Excellence`, and `Rabbi · Non Compete · Lizzette`.

### Conclusion

Version 3 resolves the HDBSCAN failure mode and surfaces substantially more semantic structure. It does not yet determine a clean natural topic count or generate a reliable taxonomy without human judgment.

The fact that the current score selected the maximum candidate of 50 is itself useful evidence: silhouette plus the present dominance penalty rewards a finer partition on this corpus. That does not mean 50 is the best number for reviewers. Product usefulness, topic coherence, and redundancy must be evaluated in addition to geometric separation.

## Review-before-apply workflow

The discovery workflow was deliberately split from application while the clustering experiments were being refined.

Discovery stores:

- The algorithm and configuration snapshot.
- The frozen document scope.
- Editable topic proposals.
- Original-space centroids.
- Extracted keywords.
- Representative excerpts.
- Sampled chunk counts.

The job then stops at `AWAITING_REVIEW`. Discovery does not create the `topics` metadata definition or write document values.

A matter administrator can rename, redescribe, or exclude proposals. Applying the reviewed set creates or updates the stable multi-value `topics` enum and starts durable assignment across the matter. Assignment defaults to replacing prior topic values for the affected documents. The review boundary protects users from automatically publishing low-quality discovery results, but it does not by itself improve cluster membership.

## Versioning and reproducibility

The algorithm version is frozen into each job configuration.

- Version 1 jobs resume with the legacy random-projection/HDBSCAN behavior.
- Version 2 jobs resume with PCA/UMAP/HDBSCAN behavior.
- New jobs use version 3 candidate KMeans behavior.

The `umap-learn` dependency remains required because version 2 jobs must remain reproducible even though new automatic jobs no longer use UMAP.

Proposal centroids are always stored in the original normalized embedding space. Dimensionality reduction is used for discovery only; it does not change the stored document vectors or the similarity space used for final assignment.

## Embedding-job caveat

The embedding job currently reports `SKIPPED` for several different cases, including reuse of an existing vector artifact and lack of usable text or chunks. An empty active normalized artifact can also result in a skip instead of falling back to faithful source text. Those cases should eventually be reported separately as `reused`, `no_usable_content`, and `failed` so clustering input coverage can be evaluated accurately.

## What has been established

The experiments support the following conclusions:

1. The one-topic result was primarily a density-clustering failure, not proof that every document had the same meaning.
2. Better text cleanup and sampling reduce bad inputs but do not alone create useful topics.
3. The existing embeddings contain meaningful subject information because fixed KMeans recovered recognizable business themes.
4. UMAP plus HDBSCAN emphasized format and repetition on this corpus.
5. Candidate KMeans is a better current basis for automatic exploration, but the present score tends toward a high topic count and does not measure reviewer usefulness.
6. Extractive names are diagnostic labels, not trustworthy final topic names.
7. Human review must remain mandatory before topic metadata is applied.
8. A topic job must preserve its algorithm and input snapshots so later code or processing changes do not alter its meaning.

## Known gaps

- There is no agreed human-evaluation set or measurable definition of a useful topic.
- Automatic candidate scoring currently selected the upper bound on the Enron corpus.
- Repeated templates, routing data, spam, and individual names can still define clusters.
- Exact duplicate suppression does not remove near-duplicate content or quoted-chain repetition.
- The review UI can rename and exclude topics, but does not yet merge similar clusters or create a broader topic from several proposals.
- The topic count is selected from a fixed candidate list rather than learned as a product-level taxonomy.
- Proposal names are extractive and can be obscure even when the underlying membership is reasonable.
- Embedding coverage metrics do not yet distinguish reuse from missing content clearly.

## Recommended next evaluation

The next step should be evaluation rather than immediately adding another clustering library.

1. Select a small, representative set of matters or corpus slices and define examples of useful reviewer-facing topics.
2. Compare fixed 20-, 30-, and 40-topic runs with the automatic version 3 result using the same sample.
3. Have a reviewer score coherence, usefulness, redundancy, and junk/template prevalence.
4. Tune the candidate range and scoring penalty from those judgments. A complexity penalty may be needed if the current score continues to prefer the maximum candidate.
5. Add merge support and an explicit `Other` or unassigned path before expecting reviewers to curate large proposal sets.
6. Improve near-duplicate and quoted-email suppression if evaluation shows those patterns still dominate membership.
7. Consider model-assisted naming only after cluster membership is acceptable. Better names cannot repair incoherent clusters.

## Operational notes

- Restart the API and workflow worker after changing clustering code or Python dependencies.
- Cancel or finish an active topic job before starting another job for the same matter.
- A newly created job uses clustering version 3; resuming an older job preserves its frozen version.
- To use newer collection cleanup rules, complete a new collection processing run, regenerate or reuse embeddings from the newly active normalized text as appropriate, and then create a new topic job.
- Worker logs record each automatic candidate's topic count, silhouette score, largest-cluster fraction, and combined score. These values should be retained when comparing runs.
